# 07 · GUI 使用说明 / GUI guide

> 起法两种，等价：
> ```bash
> python -m agentic_audioprocess.gui      # 默认 http://127.0.0.1:8402
> audio gui                        # 同上（端口 = config.server.port + 100）
> ```
> `ui.run(show=True)` 会**自动打开浏览器**。要换端口：`audio gui --port 8500`。

界面用 NiceGUI 搭，**三个功能各占一个页签**，每个都能独立调用 ——
可以只做「人声提取」，也可以只做「主体人声去除」，不必走完整流水线。

---

## 1 · 顶栏 / header

| 控件 | 说明 |
|---|---|
| 标题 | `Agentic AudioProcess <版本>` |
| **引擎下拉** | 默认选中 `uvr`；另有 `null`（零依赖占位，用于不加载权重先看界面效果） |
| **状态栏** | 实时反馈：`就绪` / `处理中…` / `完成 / done (N 轨)` / `失败` / `已上传` / `上传失败` 等，成功为绿色、失败为红色 |

引擎下拉**不加载任何权重**（能力查询是静态的），所以界面秒开。

## 2 · 素材输入 / media input

一张卡片，两种给素材的方式：

| 方式 | 操作 |
|---|---|
| **上传** | 拖拽或点击文件区（`auto_upload`，一次一个，接受 `audio/*,video/*`）。上传成功后本地路径框会被自动填入 |
| **填本地路径** | 直接在输入框粘路径（两侧带引号也能识别，会自动 strip） |

上传的文件落在 **`{output_dir}/uploads/`**，文件名只取 basename（防止客户端塞路径）。

**没有素材就点功能按钮**时，状态栏会提示「请先指定素材 / pick a media file first」；
路径写了但文件不存在，会提示「文件不存在 / not found」。两种情况都不会崩。

## 3 · 三个页签 / the three tabs

界面打开时**默认停在 ③ 主体人声去除**（本插件的核心功能）。

| 页签 | 按钮 | 做什么 |
|---|---|---|
| ① 人声提取（要所有人声） | `提取人声 / extract vocals` | 输出 `vocals` 轨 |
| ② 背景音提取（去掉所有人声） | `提取背景音 / extract accompaniment` | 输出 `accompaniment` 轨 |
| ③ 主体人声去除（保留背景人声） | `去除主体人声 / remove lead vocal` | 输出 `background` + `lead` 两轨 |

### 3.1 每次点击后发生什么

1. 状态栏变「处理中 / working…」，页签内显示「首次加载模型需要几秒」——
   首次会真的加载权重（28~67 MB，CPU）；
2. 分离在**后台线程**里跑（`run.io_bound`），界面不会被卡住；
3. 完成后页签内的旧内容被清空，换成结果：

   ```
   主体人声轨 / lead stem: vocals　判定依据 / evidence: model-convention:UVR_MDXNET_KARA.onnx->stem0
   background → demo_lead_removal_background.wav　24.00s
   [ ▶ 音频播放器 ]
   lead → demo_lead_removal_lead.wav　24.00s
   [ ▶ 音频播放器 ]
   ```

**每条轨都带内嵌播放器，点开就能直接试听效果** —— 这是刻意的设计：
分离质量必须靠耳朵判断，不该逼用户去翻目录找文件。

### 3.2 为什么把「判定依据」显示出来

去主体人声那一页会显式打印 `lead_stem` 与 `stem_order_resolved_by`。

理由是**判反方向是本插件最坏的失败模式，而且不会报错**：产出的文件看起来完全正常，
只是「去掉主体人声」被做成了「去掉背景人声」。把依据摆在界面上，
用户一眼能看出这次是靠什么判的（模型约定表 / 配置 / VAD），
配合两条轨的播放器就能立刻确认方向对不对。

详见 `01_design.md §4.1` 与 `issues/005`。

### 3.3 产物位置

| 来源 | 目录 |
|---|---|
| GUI 分离结果 | `{output_dir}/gui/` |
| GUI 上传的素材 | `{output_dir}/uploads/` |

`{output_dir}` 默认是项目根的 `outputs/`，界面底部会显示实际路径。
文件名规则见 `04_api_reference.md §1.6`。

## 4 · 手工验证清单 / manual checklist

没有浏览器自动化测试（NiceGUI 的交互层不做单测，只锁了上传这一条路径的契约，
见 `03_unit_tests.md`）。所以下面这套**手工验证**是必要的：

| # | 步骤 | 期望 |
|---|---|---|
| 1 | `python -m agentic_audioprocess.gui` | 浏览器自动打开 8402，状态栏「就绪」，引擎下拉有 `uvr` / `null` |
| 2 | 上传一个 mp4 | 路径框被自动填入 `outputs/uploads/xxx.mp4`，状态栏提示已上传 |
| 3 | 切到 ①，点「提取人声」 | 状态栏转「处理中」，随后出现 `vocals` 轨 + 播放器；试听应只剩人声 |
| 4 | 切到 ②，点「提取背景音」 | 出现 `accompaniment` 轨；**试听应完全没有说话声**（可能只剩音乐/环境音） |
| 5 | 切到 ③，点「去除主体人声」 | 出现 `background` 与 `lead` 两轨，且顶部显示 `lead stem` 与判定依据 |
| 6 | 试听 ③ 的两条轨 | `lead` 里应是主体人声；`background` 里**主体的说话声应明显消失，而背景人声/音乐仍在** |
| 7 | 检查 `outputs/gui/` | 文件名符合 `{素材名}_{模式}_{轨名}.wav`，长度与素材一致 |
| 8 | 不选素材直接点按钮 | 状态栏红字提示「请先指定素材」，界面不崩 |
| 9 | 引擎切到 `null` 再点一次 | 立刻返回（不加载权重），用于确认界面链路本身没问题 |

第 6 步是**这个插件唯一真正重要的验收**：如果 `background` 里主体人声还在、
`lead` 里是背景人声，那说明轨道方向判反了 —— 用 `audio lead-removal --lead-index 1`
（或在配置里设 `engine.uvr.lead_stem_index`）反过来即可。

## 5 · 已知限制 / known limits

1. **主体与背景同时说话的重叠段无法完美分离。** 这是技术天花板，不是实现缺陷：
   交付说明里写的是「**显著衰减**主体人声」而不是「彻底移除」。
   主体说话停顿处、以及只有主体在说的段落，效果最好。
2. **首次点击需要等一会儿**（要加载权重，28~67 MB；具体秒数取决于磁盘，**未实测**）。
   之后同一模式内权重是复用的，很快。
3. **换模式会换权重**（三个模式用三个不同的 onnx），所以页签间来回切会各等一次。
   这是刻意取舍：UVR 的 `--two-stems` 那种「一次跑完再挑」的做法不省资源。
4. **没有浏览器端自动化测试**；界面的正确性靠上面那份手工清单保证。
5. GUI 与 HTTP 服务是**两个独立进程**，端口不同（8402 / 8302），互不依赖。
6. 上传大文件受浏览器与服务端之间的传输速度限制；服务端是流式落盘，
   不会把整个文件读进内存。
